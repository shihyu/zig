Autodoc 重構 ​

目前我們已經可以使用全新的 Autodoc，新的實現帶來了更棒的文檔閱讀體驗！

總輸出大小為 47M，經過 gzip 處理後為 5.7M！

  • src/Autodoc.zig 用於處理 ZIR 代碼（zig 編譯時產生的中間代碼），輸出 json 以便 js 使用，這就導致很多代碼無法通過某些數據重建 AST 語法樹

  • lib/docs/commonmark.js 是一個第三方的 markdown 實現，但它的特性有點太多了，例如，我們並不希望在文檔註釋中使用 HTML 標籤，因為這樣會讓源代碼的註釋無比醜陋，應當只渲染源代碼和 markdown。

  • lib/docs/ziglexer.js 是 js 中針對 zig 的語義標記實現。事實上，zig 已經在標準庫中公開了由 zig 實現的語義標記。有趣的是，andrewrk 看到這個東西被添加進來的時候應該兩眼一黑，具體可以見 Issue 16306 Issue 16490 。

  • src/autodoc/render_source.zig 是一種將 .zig 文件轉換為帶有語法高亮但不是交互式的 .zig.html 文件。

編譯產物結構（演示使用的標準庫文檔）為：

sh
 12K index.html
 32K main.js
192K main.wasm
 12M sources.tar

總輸出大小為：12M，經過 gzip 處理後為 2.3M！

可以看到，新的實現的代碼和產物都很簡潔，產物剛剛好只有 4 個文件，並且文件大小直接縮減到了 1/4 。

新的實現不僅僅是表面看上去更簡單，實際上它較之舊實現更加的強大，因為新的實現並不會處理 ZIR，而是直接讀取解析源代碼文件（sources.tar 就是打包的源代碼），這意味著它擁有完整的源代碼信息，不需要進行一些亂七八糟的推斷。

此方案是使用 zig 編寫的 WebAssembly 模塊，這允許其重用編譯器中的組件，例如分詞器，解析器和其他用於對 zig 代碼進行操作的一些程序。

通過 HTTP 請求sources.tar 文件並解壓後，會將其直接送入 Wasm 模塊的內存中，針對 tar 文件使用 std.tar 進行解析，源代碼就地進行解析，並額外進行一些計算添加 hash 表。

針對目前的實現，優化空間可以使用多線程來加速解析，但目前來看單線程已經足夠快了，似乎沒有必要。

攜帶標準庫文檔 ​

在 zig 的 0.11.0 中，zig 發行時會帶有一個 docs/std/ 目錄，其中包含著舊 autodoc 實現構建產物（足足 47M 大小）。

在本次重寫中，直接刪除這些構建產物，作為代替，提供了 zig std 命令，這允許使用自帶的 autodoc 生成器來打開一個瀏覽器窗口查看文檔說明，首次使用此命令時，會先執行一次針對 lib/compiler/std-docs.zig 的編譯操作。

HTTP 服務器會動態創建請求的文件，包括 main.wasm 重建（如果任何源文件發生更改）和構造 sources.tar，這意味著在查看文檔時，對文檔文件或 autodoc 系統本身的任何源更改都會立即反映出來。在 URL 前面加上 /debug URL 會使用 WebAssembly 模塊的調試版本。

這意味著貢獻者可以通過在瀏覽器窗口中按刷新來測試對 Zig 標準庫文檔以及 autodocs 功能的更改，只需要 Zig 的二進制發行版。

總之，這使得 zig 的安裝大小從 317M 減少到了 268M（-15%）。

編譯器的 ReleaseSmall 版本從 10M 縮小到 9.8M（-1%）。

Autodoc 新特性 ​

  • 更加可靠的鏈接：由於擁有完整的源代碼，故我們擁有所有元信息，並且可以編寫更強大的代碼來從它們出現的上下文中查找標識符。

  • 交互式源列表：只要按下 u，你可以立刻查看當前聲明或者定義的源代碼（通過更改 location 哈希實現）！

  • 更加清晰的列表

  • 搜索支持註釋

  • 更加友好的錯誤集合展示（支持通過其他的聲明進行跳轉）

  • 函數說明也會展示錯誤類型說明

  • 正確的類型檢測（舊實現可能會猜錯）

  • 瀏覽歷史的正確記錄（依賴於 popstate 事件 和歷史記錄 api）

Windows 資源 ​

Zig 現在支持編譯（和交叉編譯）Windows 資源腳本（.rc文件）和 .manifest 文件，並將結果.res 文件鏈接到 PE/COFF 二進制文件的資源表中。

  • Add a .rc -> .res compiler to the Zig compiler
  • Add zig rc subcommand, a (cross-platform) drop-in replacement for rc.exe
  • Add preliminary support for Windows .manifest files

查看 Zig is now also a Windows resource compiler，瞭解這個功能的一些用例和使用細節。

鏈接器 ​

Zig 現在支持 x86_64、aarch64 的 ELF 鏈接，並部分支持 riscv64。對 LLD 的依賴預計將在下一個發佈週期中被刪除。可以使用 -fno-lld 標誌來使用當前不是默認的 Zig 鏈接器。

Bug 修復 ​

本次發佈週期一共修復了 502 個 bug。

Comptime 指針訪問 ​

Zig 在編譯期訪問指針有幾個長期存在的錯誤。當試圖以特殊的方式訪問指針，例如加載數組的切片或重新解引用內存時，你有時會遇到一個錯誤的編譯錯誤，編譯器會要求 comptime 解引用需要具有明確定義的佈局的類型。

#19630 的合併解決了這個問題。在 0.12.0 中，編譯器在進行與編譯期內存有關的複雜操作時，不再報告錯誤的編譯錯誤。這個改變也包括對編譯期 @bitCast 邏輯的一些修復；特別是，包含指針的位轉換聚合不再錯誤地強制在運行時進行操作。

Zig 目前存在一些 已知的 bugs，甚至包含一些 編譯錯誤！

工具鏈 ​

LLVM 17 ​

當前發佈的新版本已經更新至 LLVM 17.0.6！

Zig 現在直接生成 LLVM bitcode 模塊文件，然後將這些文件傳遞給 LLVM。這意味著一個沒有 LLVM 庫的 Zig 編譯器仍然可以生成 .bc 文件，然後這些文件可以傳遞給 clang 進行編譯。

musl 1.2.4 ​

儘管 musl v1.2.5 現在在上游可用，但這個版本的 Zig 仍然提供 v1.2.4。預計 Zig 的下一個版本將使用新的的 musl。

glibc 2.38 ​

當進行交叉編譯時，現在可以使用 glibc 版本 2.35、2.36、2.37 和 2.38。

mingw-w64 ​

根據 Martin Storsjö 的建議，Zig 現在跟蹤 mingw-w64 的最新主分支提交。

路線圖 ​

0.13.0 發佈週期的主要主題將是 編譯速度。

在 0.13.0 發佈週期中儘量實現一些里程碑特性：

  • 將 x86 後端作為調試模式的默認後端。
  • 鏈接器支持 COFF，移除對 LLD 的依賴。
  • 啟用增量編譯以快速重建。
  • 引入併發性到語義分析以進一步提高編譯速度。

目前的思路是，優先考慮更快的編譯將提高編譯器本身的開發速度，從而在接下來的發佈週期中修復更多的錯誤並完成更多的功能。

加快編譯速度也可能會對語言本身做出一些調整。

Async/Await 特性進度 ​

在 0.11.0 版本發佈後，異步函數被凍結。由於多個尚未解決的問題，尚不知未來如何處理該特性：

  • LLVM 無法優化它們。
  • 第三方調試器無法調試它們。
  • 取消問題。
  • 異步函數指針阻止了堆棧大小的知曉。

這些問題是可以克服的，但需要時間，Zig 團隊目前正在關注其他優先事項。
