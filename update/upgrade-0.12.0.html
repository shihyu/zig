On this page

本篇文檔將介紹如何從 0.11.0 版本升級到 0.12.0。

語言變動 ​

非必要不使用 var ​

引入了一個新的編譯錯誤，當局部變量聲明為 var 但使用 const 就足夠時，編譯器會發出該錯誤！

zig
const expectEqual = @import("std").testing.expectEqual;
test "unnecessary use of var" {
    var x: u32 = 123;
    try expectEqual(123, x);
}
sh
$ zig test unnecessary_var.zig
docgen_tmp/unnecessary_var.zig:3:9: error: local variable is never mutated
    var x: u32 = 123;
        ^
docgen_tmp/unnecessary_var.zig:3:9: note: consider using 'const'

解決該錯誤也很簡單，使用 const 即可！

結果位置語義 ​

對結果位置語義 Result Location Semantics (RLS) 的多項增強。

INFO

結果位置語義是 Zig 語言中的一個特性，它影響函數如何返回結果和錯誤。

結果類型（result types）可以通過取地址運算符（&）進行傳遞。這允許依賴結果類型的語法結構，如匿名初始化 .{ ... } 和像 @intCast 這樣的轉換內建函數，在存在取地址運算符的情況下正確地工作。這是一種新的特性，可以使代碼在處理結果類型時更加靈活和準確。

zig
const S = struct { x: u32 };
const int: u64 = 123;
const val: *const S = &.{ .x = @intCast(int) };
comptime {
    _ = val;
}

INFO

此外，在這個版本中，結果位置（result locations）不能通過 @as 和明確類型的聚合初始化 T{ ... } 進行傳播。這個限制是為了簡化語言設計。在之前的版本中，有幾個關於結果指針（result pointers）錯誤轉換的 bug，這個更改就是為了解決這些問題。

解構語法（Aggregate Destructuring） ​

引入了新語法，允許對可索引的聚合結構（如元組、向量和數組）進行解構。在賦值操作的左側編寫一系列的左值或本地變量聲明，將嘗試解構右側指定的值。這是一種新的賦值方式，可以更方便地從聚合結構中提取值：

zig
var z: u32 = undefined;
const x, var y, z = [3]u32{ 1, 2, 3 };
y += 10;
// x 是 1，y 是 2，z 是 3

const x, const y = @Vector(2, u32){ 1, 2 };
// 編譯期的值也會進行解構，x 是 1，y 是 2

var runtime: u32 = undefined;
runtime = 123;
const x, const y = .{ 42, runtime };
// 當然，編譯期和運行時的值也會被正確解析
// x 是編譯期可以知道的值 42
// y 是運行時可知的值 123

WARNING

切片（slices）不能直接被解構，如果想從切片中解構值，需要將它轉換為數組，方法是使用編譯時已知的邊界進行切割，例如 slice[0..3].*。這樣，就可以像處理數組一樣處理切片，從而實現解構。

命名空間類型等價性 ​

在 Zig 中，結構體（struct）、枚舉（enum）、聯合體（union）和不透明類型（opaque types）是特殊的，它們不像元組和數組那樣使用結構等價性，而是創建獨特的類型。這些類型有命名空間，因此可能包含聲明，它們可以統稱為"命名空間類型"。

在 0.11.0 版本中，每次這樣的類型聲明被語義分析時，都會創建一個新的類型。泛型類型的等價性是通過對編譯時函數調用的記憶化（memoization）來處理的；也就是說，std.ArrayList(u8) == std.ArrayList(u8) 成立，因為 ArrayList 函數只被調用一次，其結果被記憶化。

在 0.12.0 版本中，這一點發生了變化。現在，命名空間類型基於兩個因素進行去重：它們的源位置和它們的捕獲。

類型的"捕獲"指的是它閉包覆蓋的編譯時已知類型和值的集合。換句話說，它是在類型內部引用但在類型外部聲明的值的集合。例如，std.ArrayList 的編譯時 T: type 參數被它返回的類型捕獲。如果兩個命名空間類型由同一段代碼聲明並且有相同的捕獲，那麼它們現在被認為是完全相同的類型。

請注意，編譯器仍然會記憶化編譯時調用：這一點沒有改變。然而，這種記憶化對語言語義的影響已經不再有意義。

這種實現的更改不太可能帶來改變，但需要注意以下情況：

zig
fn MakeOpaque(comptime n: comptime_int) type {
    _ = n;
    return opaque {};
}
const A = MakeOpaque(0);
const B = MakeOpaque(1);

在 Zig 0.11.0 版本中，這段代碼會創建兩個不同的類型，因為對 MakeOpaque 的調用是不同的，因此每次調用都會單獨分析不透明聲明。而在 Zig 0.12.0 版本中，這些類型是相同的（A == B），因為雖然函數被調用了兩次，但聲明並沒有捕獲任何值。

要修正這個問題也很簡單，強制捕獲 n 就可以了：

zig
fn MakeOpaque(comptime n: comptime_int) type {
    return opaque {
        comptime {
            _ = n;
        }
    };
}
const A = MakeOpaque(0);
const B = MakeOpaque(1);

由於 n 被 opaque 強制引用，將會產生兩個不同的類型！

編譯期內存變化 ​

對編譯器的編譯時內存（comptime memory）的內部表示，特別是編譯時可變內存（即 comptime var）進行了全面改革。這次改革帶來了一些面向用戶的變化，以新的限制的形式出現，限制了你可以對 comptime var 做什麼。

第一個也是最重要的新規則是，永遠不允許指向 comptime var 的指針成為運行時已知的。例如：

zig
test "runtime-known comptime var pointer" {
    comptime var x: u32 = 123;
    // `var` 使得 `ptr` 運行時可知
    var ptr: *const u32 = undefined;
    ptr = &x;
    if (ptr.* != 123) return error.TestFailed;
}
sh
$ zig test comptime_var_ptr_runtime.zig
docgen_tmp/comptime_var_ptr_runtime.zig:5:11: error: runtime value contains reference to comptime var
    ptr = &x;
          ^~
docgen_tmp/comptime_var_ptr_runtime.zig:5:11: note: comptime var pointers are not available at runtime

在早期版本的 Zig 中，此測試會通過。現在，編譯器會報告編譯錯誤，因為對 ptr 的賦值使得值 &x（這是一個指向 comptime var 的指針）變為運行時已知。

例如，通過將這樣的指針傳遞給在運行時調用的函數，這些指針也可以變為運行時已知：

zig
test "comptime var pointer as runtime argument" {
    comptime var x: u32 = 123;
    if (load(&x) != 123) return error.TestFailed;
}
fn load(ptr: *const u32) u32 {
    return ptr.*;
}
sh
$ zig test comptime_var_ptr_runtime_arg.zig
docgen_tmp/comptime_var_ptr_runtime_arg.zig:3:14: error: runtime value contains reference to comptime var
    if (load(&x) != 123) return error.TestFailed;
             ^~
docgen_tmp/comptime_var_ptr_runtime_arg.zig:3:14: note: comptime var pointers are not available at runtime

現在，這個測試也會發出一個編譯錯誤。load 的調用發生在運行時，它的 ptr 參數沒有標記為 comptime，所以在 load 的主體內，ptr 是運行時已知的。這意味著調用 load 使得指針 &x 在運行時已知，因此產生了編譯錯誤。

這個限制是為了修復一些反直覺的錯誤。當一個指向 comptime var 的指針變為運行時已知時，對它的修改變得無效，因為指向的數據變為常量，但類型系統沒有反映這一點，導致在看似有效的代碼中可能出現運行時段錯誤。此外，你在運行時從這樣的指針讀取的值將是它的"最終"編譯時值，這是一種不直觀的行為。因此，這些指針不能再是運行時已知的。

第二個新的限制是一個指向 comptime var 的指針永遠不允許包含在全局聲明的解析值中。例如：

zig
const ptr: *const u32 = ptr: {
    var x: u32 = 123;
    break :ptr &x;
};
comptime {
    _ = ptr;
}
sh
$ zig test comptime_var_ptr_global.zig
docgen_tmp/comptime_var_ptr_global.zig:1:30: error: global variable contains reference to comptime var
const ptr: *const u32 = ptr: {
                        ~~~~~^
referenced by:
    comptime_0: docgen_tmp/comptime_var_ptr_global.zig:6:9
    remaining reference traces hidden; use '-freference-trace' to see all reference traces

在這裡，ptr 是一個全局聲明，其值是一個指向 comptime var 的指針。這個聲明在 0.11.0 中是允許的，但在 0.12.0 中會引發一個編譯錯誤。在更復雜的情況下，同樣的規則也適用，例如當指針包含在結構體字段中時：

zig
const S = struct { ptr: *const u32 };
const val: S = blk: {
    var x: u32 = 123;
    break :blk .{ .ptr = &x };
};
comptime {
    _ = val;
}
sh
$ zig test comptime_var_ptr_global_struct.zig
docgen_tmp/comptime_var_ptr_global_struct.zig:2:21: error: global variable contains reference to comptime var
const val: S = blk: {
               ~~~~~^
referenced by:
    comptime_0: docgen_tmp/comptime_var_ptr_global_struct.zig:7:9
    remaining reference traces hidden; use '-freference-trace' to see all reference traces

這段代碼引發的編譯錯誤與前一個例子相同。這個限制主要是為了幫助在 Zig 編譯器中實現增量編譯，這依賴於全局聲明的分析是順序無關的，以及聲明之間的依賴關係可以被輕易地建模。

這種情況最常見的表現形式是在現有代碼中出現編譯錯誤，如果一個函數在編譯時構造一個切片，然後在運行時使用。例如，考慮以下代碼：

zig
fn getName() []const u8 {
    comptime var buf: [9]u8 = undefined;
    // 在實踐中，這裡可能會有更復雜的邏輯來填充 buf
    @memcpy(&buf, "some name");
    return &buf;
}
test getName {
    try @import("std").testing.expectEqualStrings("some name", getName());
}
sh
$ zig test construct_slice_comptime.zig
docgen_tmp/construct_slice_comptime.zig:5:12: error: runtime value contains reference to comptime var
    return &buf;
           ^~~~
docgen_tmp/construct_slice_comptime.zig:5:12: note: comptime var pointers are not available at runtime
referenced by:
    decltest.getName: docgen_tmp/construct_slice_comptime.zig:8:64
    remaining reference traces hidden; use '-freference-trace' to see all reference traces

調用 getName 返回一個切片，其 ptr 字段是一個指向 comptime var 的指針。這意味著這個值不能在運行時使用，也不能出現在全局聲明的值中。這段代碼可以通過在填充緩衝區後將計算的數據提升為 const 來修復：

zig
fn getName() []const u8 {
    comptime var buf: [9]u8 = undefined;
    // In practice there would likely be more complex logic here to populate `buf`.
    @memcpy(&buf, "some name");
    const final_name = buf;
    return &final_name;
}
test getName {
    try @import("std").testing.expectEqualStrings("some name", getName());
}

像在 Zig 的早期版本中一樣，編譯時已知的 consts 具有無限的生命週期，這裡討論的限制不適用於它們。因此，這段代碼會正常運行。

另一種可能的失敗模式是在使用舊語義創建全局可變編譯時狀態的代碼中。例如，以下片段試圖創建一個全局的編譯時計數器：

zig
const counter: *u32 = counter: {
    var n: u32 = 0;
    break :counter &n;
};
comptime {
    counter.* += 1;
}
sh
$ zig test global_comptime_counter.zig
docgen_tmp/global_comptime_counter.zig:1:32: error: global variable contains reference to comptime var
const counter: *u32 = counter: {
                      ~~~~~~~~~^
referenced by:
    comptime_0: docgen_tmp/global_comptime_counter.zig:6:5
    remaining reference traces hidden; use '-freference-trace' to see all reference traces

這段代碼在 Zig 0.12.0 中會發出一個編譯錯誤。Zig 不支持也不會支持這種用例：任何可變的編譯時狀態必須在本地表示。

@fieldParentPtr ​

刪除了第一個參數，以支持使用結果類型。

遷移指南：

zig
const parent_ptr = @fieldParentPtr(Parent, "field_name", field_ptr);

變為：

zig
const parent_ptr: *Parent = @fieldParentPtr("field_name", field_ptr);

或者

zig
const parent_ptr: *Parent = @alignCast(@fieldParentPtr("field_name", field_ptr));

這取決於編譯器能夠證明的父指針對齊。第二種形式更具有可移植性，因為對於某些目標可能需要 @alignCast ，而對於其他目標可能不需要。

禁止在函數類型上進行對齊 ​

0.11.0 允許函數類型指定對齊。在 0.12.0 中，這是不允許的，因為它是函數聲明和指針的屬性，而不是函數類型的屬性。

zig
comptime {
    _ = fn () align(4) void;
}

會報告以下錯誤：

sh
$ zig test func_type_align.zig
docgen_tmp/func_type_align.zig:2:21: error: function type cannot have an alignment
    _ = fn () align(4) void;

@errorCast ​

過去發佈的版本包含了一個 @errSetCast 內置函數，它執行從一個錯誤集到另一個可能更小的錯誤集的安全檢查轉換。在 0.12.0 中，這個內置函數被 @errorCast 替換。它將繼續發揮原本的作用，但此外，這個新的內置函數可以轉換錯誤聯合類型的錯誤集：

zig
const testing = @import("std").testing;

test "@errorCast error set" {
    const err: error{Foo, Bar} = error.Foo;
    const casted: error{Foo} = @errorCast(err);
    try testing.expectEqual(error.Foo, casted);
}

test "@errorCast error union" {
    const err: error{Foo, Bar}!u32 = error.Foo;
    const casted: error{Foo}!u32 = @errorCast(err);
    try testing.expectError(error.Foo, casted);
}

test "@errorCast error union payload" {
    const err: error{Foo, Bar}!u32 = 123;
    const casted: error{Foo}!u32 = @errorCast(err);
    try testing.expectEqual(123, casted);
}

@abs ​

在此之前的版本包含 @fabs 內置函數，std.math.fabs() 和 std.math.abs() 標準庫函數。這已被新的 @abs 內置函數替換，它能夠對整數以及浮點數進行操作。

zig
const expectEqual = @import("std").testing.expectEqual;

test "@abs on float" {
    const x: f32 = -123.5;
    const y = @abs(x);
    try expectEqual(123.5, y);
}

test "@abs on int" {
    const x: i32 = -12345;
    const y = @abs(x);
    try expectEqual(12345, y);
}

標準庫 ​

在 Windows 上，程序的命令行參數是一個單一的 WTF-16 編碼字符串，由程序來將其分割成字符串數組。在 C/C++ 中，C 運行時的入口點負責分割命令行並將 argc/argv 傳遞給 main 函數。

以前，ArgIteratorWindows 匹配 CommandLineToArgvW 的行為，但事實證明，CommandLineToArgvW 的行為並不匹配 2008 年後的 C 運行時。在 2008 年，C 運行時的 argv 分割改變了它如何處理引用參數中的連續雙引號（現在被認為是轉義引號，例如 "foo""bar" 在 2008 年後會被解析成 foo"bar），並且 argv[0] 的規則也被改變了。

這個版本使 ArgIteratorWindows 匹配 2008 年後的 C 運行時的行為。這裡的動機大致與 Rust 做出同樣的改變時相同，即（改述）：

  • Zig 和現代 C/C++ 程序之間的一致行為

  • 允許用戶以更直接的方式轉義雙引號

此外，對 BatBadBut 的建議的緩解措施依賴於 2008 年後的 argv 分割行為，以便對給 cmd.exe 的參數進行往返處理。

BadBatBut 的緩解措施沒有在 0.12.0 版本的發佈截止日期之前完成。

不再允許覆蓋 POSIX API ​

Zig 的歷史版本允許應用程序覆蓋標準庫的 POSIX API 層。該版本故意移除了這個能力，沒有提供遷移方案。

這從一開始就是一個錯誤。在這個抽象層進行該操作是錯誤的。

對此的另一種計劃是使所有 I/O 操作都需要一個 IO 接口參數，類似於今天的分配需要一個 Allocator 接口參數。

但當前尚未有類似的規劃，所以需要該功能的應用程序必須維護一個標準庫的分支，直到該問題被解決。

std.os 命名為 std.posix ​

遷移方式：

zig
std.os.abort();

到

zig
std.posix.abort();

通常，人們應該更傾向於使用更高級別的跨平臺抽象，而不是深入到 POSIX API 層。例如， std.process.exit 比 std.posix.exit 更具有可移植性。你通常應該期望在操作系統實現相應的 POSIX 功能時，std.posix 內的 API 在給定的操作系統上是可用的。

Ryu 浮點數格式化 ​

Zig 0.12.0 用基於 Ryu 的算法替換了先前的 errol 浮點數格式化算法，Ryu 是一種用於將 IEEE-754 浮點數轉換為十進制字符串的現代算法。

這帶來的改進包括：

  • 能夠格式化 f80 和 f128 類型
  • 更準確的 f16 和 f32 格式化
  • 對每種浮點類型的完全往返支持
  • 通用後端，可以用來打印任何一般位數的浮點數（小於或等於 128 位）

差異：

  • 指數不再用前導 0 填充到 2 位，如果是正數，不再打印符號：
sh
errol: 2.0e+00
ryu:   2e0
  • 在除 f64 之外的所有情況下，全精度輸出更準確，因為我們不再在內部進行 f64 的轉換：
sh
# Ryu
3.1234567891011121314151617181920212E0 :f128
3.1234567891011121314E0 :f80
3.1234567891011121314E0 :c_longdouble
3.123456789101112E0 :f64
3.1234567E0 :f32
3.123E0 :f16

## Errol
3.123456789101112e+00 :f128
3.123456789101112e+00 :f80
3.123456789101112e+00 :c_longdouble
3.123456789101112e+00 :f64
3.12345671e+00 :f32
3.123046875e+00 :f16

此外，在這些情況下，固定精度情況下的舍入行為也可能不同，因為最短表示通常會有所不同：

sh
# bits:         141333
# precision:    3
# std_shortest: 1.98049715e-40

# type:         f32

重構 HTTP ​

首先，一些非常直接的更改：

  • 不發出 Server HTTP 頭。如果用戶希望添加，讓他們自己添加。這不是嚴格必要的，可以說是一個有害的默認設置。
  • 修正 finish 的錯誤集，不再包含 NotWriteable 和 MessageTooLong 在 Server 中防止零長度的塊
  • 在 FetchOptions 中添加缺失的重定向行為選項，並將其改為枚舉，而不是 2 個字段
  • error.CompressionNotSupported 被重命名為 error.CompressionUnsupported，與同一集合中所有其他錯誤的命名約定相匹配。
  • 刪除了與字段和類型名稱重複的文檔註釋。
  • 暫時禁用服務器中的 zstd 解壓縮；參見 #18937。
  • Automatically handle expect: 100-continue requests

接下來，移除了堆分配頭部緩衝區的能力。HTTP 頭部的緩衝區現在總是通過靜態緩衝區提供。因此，OutOfMemory 不再是 read() 錯誤集的成員，Client 和 Server 的 API 和實現得到了簡化。error.HttpHeadersExceededSizeLimit 被重命名為 error.HttpHeadersOversize。

大的變動：

移除 std.http.Headers ​

相反，一些頭部通過在解析 HTTP 請求/響應時填充的顯式字段名提供，一些通過支持傳遞額外、任意頭部的新字段提供。這在許多地方簡化了邏輯，也消除了許多地方的失敗可能性。現在進行的反初始化代碼更少了。此外，它使得不再需要克隆頭部數據結構來處理重定向。

http_proxy 和 https_proxy 字段現在是指針，因為它們通常未被填充。

將 loadDefaultProxies 改為 initDefaultProxies ，以表明它實際上並未從磁盤或網絡加載任何東西。現在的函數是有洩漏的；API 用戶必須傳遞一個已經實例化的競技場分配器。消除了反初始化代理的需要。

以前，代理存儲了任意的頭部集合。現在它們只存儲授權值。

刪除了 https_proxy 和 http_proxy 之間的重複代碼。最後，環境變量的解析失敗會導致錯誤被髮出，而不是默默地忽略代理。

完全重構 Server ​

主要移除了名字起得不好的 wait、send、finish 函數，它們都在同一個"Response"對象上操作，實際上這個對象被用作請求。

現在，看起來像：

  • std.net.Server.accept() 會給出一個 std.net.Server.Connection
  • 使用 connection 初始化 std.http.Server.init()
  • Server.receiveHead() 會給出一個 Request
  • Request.reader() 給出一個 body 的 reader
  • Request.respond() 是一次性的，或者 Request.respondStreaming() 創建一個Response
  • Response.writer() 給出一個 body 的 writer
  • Response.end() 完成響應；Response.endChunked() 允許傳遞響應尾部。

換句話說，類型系統現在引導 API 用戶走正確的路徑。

receiveHead 允許將額外的字節讀入讀緩衝區，然後將這些字節用於主體或在連接複用時用於下一個請求。

respond()，一次性函數，將在一次系統調用中發送整個響應。

流式響應體不再浪費地用塊頭和尾部包裝每次寫入調用；相反，它只在刷新時發送 HTTP 塊 wrapper。這意味著用戶仍然可以控制何時發生，它也不會添加不必要的塊。

從經驗上看，使用代碼顯著地減少了噪音，它在更正確地處理錯誤的同時減少了錯誤處理，更明確地顯示了正在發生的事情，並且是使用系統調用優化的。

zig
var read_buffer: [8000]u8 = undefined;
    accept: while (true) {
        const connection = try http_server.accept();
        defer connection.stream.close();

        var server = std.http.Server.init(connection, &read_buffer);

deflate 的重實現 ​

deflate 是一種無損數據壓縮算法和相關的文件格式。它通常用於 gzip 和 zip 文件格式中，也是 HTTP 協議中的一種常見的內容編碼方式。

inflate 是一種數據解壓縮算法，它是 deflate 壓縮算法的反向操作。在網絡傳輸或數據存儲中，通常先使用 deflate 算法將數據壓縮，然後在需要使用數據時，再使用 inflate 算法將數據解壓縮回原始形式。

在 0.11.0 中，deflate 實現是從 Go 標準庫移植過來的，它有一些不受歡迎的特性，如不恰當地使用了全局變量，在 Zig 的代碼庫中關於 Go 的優化器的評論，以及需要動態內存分配。

0.12.0 重構了整個實現，並不是單純的移植！

新的實現在解壓縮上大約快 1.2 - 1.4 倍，在壓縮上快 1.1 - 1.2 倍。在兩種情況下，壓縮大小几乎相同（來源）。

新的代碼對所有結構使用靜態分配，不需要分配器。這對於 deflate 很有意義，因為所有的結構、內部緩衝區獲得了大小剛好的內存。對於 inflate 來說，相較過去的實現通過不預分配到理論最大尺寸數組（申請的數組通常不會被完全使用）來減少內存使用。

對於 deflate，新的實現分配了 395K，而之前的實現使用了 779K。對於 inflate，新的實現分配了 74.5K，而舊的實現大約 36K。

inflate 的差異是因為我們在這裡使用 64K 的歷史記錄，而之前是 32K。

pub fn new(comptime pkg: type, allocator: std.mem.Allocator) !void {
    var buf = std.ArrayList(u8).init(allocator);
    defer buf.deinit();

    // Compressor
    var cmp = try pkg.compressor(buf.writer(), .{});
    _ = try cmp.write(data);
    try cmp.finish();

    var fbs = std.io.fixedBufferStream(buf.items);
    // Decompressor
    var dcp = pkg.decompressor(fbs.reader());

    const plain = try dcp.reader().readAllAlloc(allocator, std.math.maxInt(usize));
    defer allocator.free(plain);
    try std.testing.expectEqualSlices(u8, data, plain);

pub fn oldDeflate(allocator: std.mem.Allocator) !void {
    const deflate = std.compress.v1.deflate;

    // Compressor
    var buf = std.ArrayList(u8).init(allocator);
    defer buf.deinit();
    // Remove allocator
    // Rename deflate -> flate
    var cmp = try deflate.compressor(allocator, buf.writer(), .{});
    _ = try cmp.write(data);
    try cmp.close(); // Rename to finish
    cmp.deinit(); // Remove

    // Decompressor
    var fbs = std.io.fixedBufferStream(buf.items);
    // Remove allocator and last param
    // Rename deflate -> flate
    // Remove try
    var dcp = try deflate.decompressor(allocator, fbs.reader(), null);
    defer dcp.deinit(); // Remove

    const plain = try dcp.reader().readAllAlloc(allocator, std.math.maxInt(usize));
    defer allocator.free(plain);
    try std.testing.expectEqualSlices(u8, data, plain);
}

POSIX 的 termios 是一個用於控制終端 I/O 特性的數據結構。它包含了一系列的標誌位和設置，用於控制輸入、輸出和控制字符的處理方式，以及其他的終端相關設置。例如，你可以通過修改 termios 結構來設置終端的波特率、字符大小、奇偶校驗等參數。

指針保護鎖（Pointer Stability Locks） ​

"Pointer Stability Locks" 是一種用於保護數據結構中的指針不被非法修改的機制。在 Zig 中，你可以使用 std.debug.SafetyLock 來鎖定指針，防止它們在不應該被修改的時候被修改。如果嘗試在鎖定後修改這些指針，程序會拋出一個 panic，而不是觸發未定義的行為。這可以幫助開發者更容易地發現和修復可能的錯誤。

添加了 std.debug.SafetyLock ，標準庫的哈希表中新添加的 lockPointers() 和 unlockPointers() 用到了它。

除了觸發未定義行為外，這提供了一種新的方法來檢測非法修改和 panic。

const std = @import("std");

pub fn main() !void {
    const gpa = std.heap.page_allocator;
    var map: std.AutoHashMapUnmanaged(i32, i32) = .{};

    const gop = try map.getOrPut(gpa, 1234);
    map.lockPointers();
    defer map.unlockPointers();

    gop.value_ptr.* = try calculate(gpa, &map);
}

fn calculate(gpa: std.mem.Allocator, m: anytype) !i32 {
    try m.put(gpa, 42, 420);
    return 999;
}

引入 b.path，棄用 LazyPath.relative ​

這將 *std.Build 所有者添加到 LazyPath ，以便可以在應用程序的構建腳本中順利使用從依賴項返回的懶惰路徑。

遷移指南：

在 source 中使用相對地址：

zig
.root_source_file = .{ .path = "src/main.zig" },

↓

zig
.root_source_file = b.path("src/main.zig"),

LazyPath.relative：

zig
.root_source_file = LazyPath.relative("src/main.zig"),

↓

zig
.root_source_file = b.path("src/main.zig"),

測試運行器：

zig
.test_runner = "path/to/test_runner.zig",

↓

zig
.test_runner = b.path("path/to/test_runner.zig"),

Header 安裝 ​

Compile.installHeader和其它相關函數的目的一直是將頭文件與產物一起打包，讓它們與產物一起安裝，並自動添加到與產物鏈接的模塊的包含搜索路徑中。

然而，在 0.11.0 中，這些函數修改了構建器的默認 install 頂級步驟，導致了一些意想不到的結果，比如根據調用的頂級構建步驟的不同，可能會安裝或不安裝頭文件。

0.12.0 將其改為將安裝的頭文件添加到編譯步驟本身，而不是修改頂級安裝步驟。為了處理依賴鏈接模塊的包含搜索路徑的構建，第一次有模塊鏈接到工件時，會創建並設置一個負責構建適當包含樹的中間 WriteFile 步驟。

遷移指南：

Compile.installHeader 現在接收一個 LazyPath:

zig
for (headers) |h| lib.installHeader(h, h);

↓

zig
for (headers) |h| lib.installHeader(b.path(h), h);

Compile.installConfigHeader 已經移除了它的第二個參數，現在使用 include_path 的值作為它的子路徑，以與 Module.addConfigHeader 保持一致。如果你想將子路徑設置為其他內容，可以使用 artifact.installHeader(config_h.getOutput(), "foo.h")。

zig
lib.installConfigHeader(avconfig_h, .{});

↓

zig
lib.installConfigHeader(avconfig_h);

Compile.installHeadersDirectory / installHeadersDirectoryOptions 已經合併為 Compile.installHeadersDirectory ，它接受一個 LazyPath，並允許像 InstallDir 一樣使用 exclude/include 過濾器。

zig
lib.installHeadersDirectoryOptions(.{
        .source_dir = upstream.path(""),
        .install_dir = .header,
        .install_subdir = "",
        .include_extensions = &.{
            "zconf.h",
            "zlib.h",
        },
    });

↓

zig
lib.installHeadersDirectory(upstream.path(""), "", .{
        .include_extensions = &.{
            "zconf.h",
            "zlib.h",
        },
    });

額外內容：

  • b.addInstallHeaderFile 現在需要一個 LazyPath。

  • 作為 resurrect emit-h 的解決方法，即使用戶指定了 h_dir 覆蓋，-femit-h 生成 header 也不會被觸發。如果你的確需要觸發生成 header，你現在需要使用 install_artifact.emitted_h = artifact.getEmittedH()，直到 -femit-h 被修復。

  • 添加了 WriteFile.addCopyDirectory，其功能與 InstallDir 非常相似。

  • InstallArtifact 已經更新，可以將打包的頭文件與產物一起安裝。打包的頭文件將安裝到由 h_dir 指定的目錄（默認為 zig-out/include）。

移除 vcpkg 的支持 ​

vcpkg 是微軟提供的一個 C/C++ 包管理工具，在之前的版本中可以用 addVcpkgPaths 方法來鏈接使用 vcpkg 安裝的包，但在 579f572c 這個 commit 中 Andrew 刪除的對它的支持。推薦使用 zon 的方式來管理依賴。

可以想到，這樣短時間內會比較麻煩，如果自己用到的包沒有用 zig build，需要自己包裝一下，但長遠來看是有利於 Zig 生態的，畢竟常用的包不會多，社區經過一段時間發展，常見的 C 庫應該都會有對應的 Zig 版本。

dependencyFromBuildZig ​

給定一個對應於依賴項的 build.zig 的結構，b.dependencyFromBuildZig 返回相同的依賴項。換句話說，如果你已經 @import 了一個依賴項的 build.zig 結構，你可以使用這個函數來獲取一個對應的 Dependency：

zig
// in consumer build.zig
const foo_dep = b.dependencyFromBuildZig(@import("foo"), .{});

上面代碼會根據 foo 這個導入返回它的 build.zig 的整個頂層空間。

這個函數對於從它們的 build.zig 文件中暴露需要使用它們對應 Dependency 的函數的包來說是有用的，比如用於訪問包相對路徑，或者運行系統命令並返回輸出為懶加載路徑。現在可以通過以下方式來實現：

zig
// in dependency build.zig
// 假設這裡是 A
pub fn getImportantFile(b: *std.Build) std.Build.LazyPath {
    const this_dep = b.dependencyFromBuildZig(@This(), .{});
    return this_dep.path("file.txt");
}

// in consumer build.zig
// 假設這裡是 B
const file = @import("foo").getImportantFile(b);

我們可以在 B 中獲取 A 的 build.zig 頂層空間，例如我們可以使用這個 build.zig 暴露出的其他構造函數！這有助於提高包的靈活性。
