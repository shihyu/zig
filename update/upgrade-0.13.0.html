標準庫 ​

BatBadBut 漏洞臨時方案 ​

std.process.Child：針對 Windows 上的任意命令執行漏洞 (BatBadBut) 的臨時解決方案！

更多信息可以見該 Issue 和該文章 BatBadBut: You can't securely execute commands on Windows。

簡化 hash.crc 實現 ​

移除了兩個原始實現，轉而採用基於算法類型的泛型實現。過去有三個很相似的實現，這令人在選擇時感到迷惑！

庫普曼多項式（Koopman polynomial）沒有完全等價的多項式，因此已將其添加到 catalog.txt 文件中。未來更新時測試會報告此問題。

對於舊庫普曼多項式 api 的用戶來說，這是一個重大變化，特別是在使用自定義或非標準多項式時（Crc32 別名將繼續起作用）。編譯錯誤會說明需要做什麼才能保留現有功能，可能需要用戶進行少量代碼更改。

zig
const hash = Crc32WithPoly(.Castagnoli); // old
const hash = Crc(.Crc32Iscsi); // new

自定義多項式需要更多的處理，並且需要用戶定義自己的算法類型。如果使用，請注意之前的實現需要預反射多項式並使用以下參數：

zig
.{
    .polynomial = 0x741b8cd7, // equivalent to the reflected polynomial: 0xeb31d82e
    .initial = 0xffffffff,
    .reflect_input = true,
    .reflect_output = true,
    .xor_output = 0xffffffff,
}

重命名 ComptimeStringMap 為 StaticStringMap ​

重命名後的 StaticStringMap 僅接受單個類型參數，並返回已知的結構類型而不是匿名結構。這些更改最初的目的是為了減少 #19682 中描述的“過長類型名稱”問題。

但缺點是對 API 進行了破壞，新的使用方法如下：

zig
const map = std.StaticStringMap(T).initComptime(kvs_list);

更多細節：

  • 將 kvs_list 參數從類型參數移至 initComptime() 參數
  • 新的公共方法：
    • keys() 、values()
    • init(allocator)、deinit(allocator) 用於運行時數據
    • 暫時保留 getLongestPrefix(str)、getLongestPrefixIndex(str)，或許仍有用
  • 性能指標：
    • 基準測試結果：travisstaloch/comptime-string-map-revised#1
    • 將結構體大小從 48 字節減少到 32 字節，從而對所有長度字段使用 u32 而不是 usize，從而提高速度
    • 將 KV 存儲為數組結構體可提高速度
    • 最新的基準測試顯示了 debug / safe / small / fast 的 wall_time 改進：-6.6% / -10.2% / -19.1% / -8.9%

PriorityQueue 存儲容量而不是長度 ​

這是一項重大更改，使 PriorityQueue 與 ArrayList 保持一致。

此前，PriorityQueue 將整個分配的切片存儲在 items 字段中，並將長度存儲在單獨的 len 字段中。這與 ArrayList 不一致，導致訪問內存越界錯誤。

現在，items 字段僅指向隊列中的有效項目，額外未使用的容量存儲在單獨的 cap 字段中。

具體見此處：std: align PriorityQueue and ArrayList API-wise。

重命名 std.ChildProcess 為 std.process.Child ​

此前 std.ChildProcess 就已經處於棄用狀態！

升級指南：

zig
std.ChildProcess

↓

zig
std.process.Child

NOTE

還有一些其他的函數也從 std.ChildProcess 移動到 std.process 命名空間。 未來還會有重大變化。例如，不使用創建一個 Child，然後在其上設置字段，然後調用 spawn，而是使用 std.process.spawn ，它採用 options 參數，然後返回 Child，只是一個從 spawn 到 termination 狀態的對象。這是在 Zig 中更傾向於採用的一種做法，即將類型設計為具有最小生命週期和儘可能少未定義字段的狀態。

重構 CLI Progress ​

這是對標準庫的重大更改。編譯器和構建系統都嚴重依賴此 API，因此受到影響。

  • 簡單的 asciinema source code
  • 使用 zig build 構建音樂播放器 source code
  • 性能影響可以忽略不計

升級指南：

  • 傳遞 std.Progress.Node 而不是 *std.Progress.Node （不再是指針）
  • 移除對 node.activate() 的調用，已不再需要
  • 現在可以直接將短存活期的字符串傳遞給 Node.start ，因為數據將被複制
  • 多次初始化 std.Progress 是非法的，請僅在 main() 中進行初始化
  • 在寫入 stderr 之前使用 std.debug.lockStdErr 和 std.debug.unlockStdErr 來正確集成到 std.Progress（ std.debug.print 內部已經包含該操作）
zig
var progress = std.Progress{
    ...
};
const root_node = progress.start("Test", test_fn_list.len);

↓

zig
const root_node = std.Progress.start(.{
    .root_name = "Test",
    .estimated_total_items = test_fn_list.len,
});

start 的所有選項都是可選的，當生成子進程時，首先填充 progress_node 字段：

zig
child.progress_node = node;
try child.spawn();

>`std.Progress` 過去的實現存在限制，即它無法確定終端的所有權。這意味著它只能通過打印到終端的內容來處理子進程，並且它必須處理無進度感知的 stderr 寫入終端。它還禁止處理 `SIGWINCH` 和使用 `ioctl` 來查找終端的行列。

新實現的設計理念是，單個進程將直接控制終端，所有其他進度報告都將傳回該進程，這可以按照需求隨意定製進度條。

創建一個標準的“Zig Progress Protocol”來使用，方便當應用程序是終端所有者或者當應用程序是子進程時，std.Progress API 都可以正常工作。後者的進度信息將通過管道以語義方式傳遞給父進程。

文件描述符通過 ZIG_PROGRESS 環境變量給出，方便 std.process.Child 與其集成，因此在父進程中附加子進程的進度就像在調用 spawn 之前設置 child.progress_node 字段一樣簡單。

為了避免使用此 API 帶來的性能損失，Node.start 和 Node.end API 是線程安全的、無鎖的、絕對可靠的，並且執行最少量的內存加載和存儲。為了實現這一點，使用了靜態分配的 Node 存儲緩衝區：一塊用於父項，另外的用於其餘數據，子項不被存儲。靜態分配的緩衝區用於定製的 Node 分配器實現。

事實上，靜態緩衝區完全夠用，因為可以設置支持的終端寬度和高度的上限。如果終端大小超過此值，進度條輸出無論如何都會被截斷。

實現的大致原理

一個單獨的線程通過計時器定期刷新終端，該進度更新線程迭代整個預分配的父數組，查找已使用的節點。這非常高效，因為雙親數組只有 200 個 8 位整數，或者大約 4 個高速緩存行。

迭代時，該線程通過從共享數據原子加載到僅由單個線程（進度更新線程）訪問的數據，將數據“序列化”到單獨的預分配數組中。

之後查找被標記為文件描述符的節點（通向子進程的管道），這些節點在序列化過程中將處理從管道中讀取的數據。除了需要重新定位的父數組之外，數據可以按位進行 memcpy。一旦序列化過程完成，就會有兩個路徑，一個是子進程，另一個是擁有終端的根進程。

擁有終端的根進程掃描序列化數據，計算子進程和同級指針。序列化的數據僅包含父節點，因此在計算時，會從這裡開始。然後遍歷樹，附加到一個靜態緩衝區，該緩衝區將通過單個 write() 系統調用發送到終端。在此過程中，會考慮檢測到的終端行和列。如果用戶調整終端大小，則會導致 SIGWINCH 信號，通知更新線程喚醒並使用新行和列重新繪製。

子進程並不是繪製到終端，而是獲取相同的序列化數據並通過管道發送它。管道處於非阻塞模式，因此如果管道已滿，則子進程將丟棄消息；未來的更新將包含新的進度信息。同樣，當父進程從管道中讀取消息時，它會丟棄緩衝區中除最後一條消息之外的所有消息。如果管道中沒有消息，父級將使用上次更新的數據。
