語法變動 ​

標記 switch ​

Zig 官方團隊接受了一個新的提案，該提案允許對 switch 語句進行標記，並允許其成為 continue 語句跳轉的目標。此處的 continue 語句接受單個操作數（類似 break 可以從塊或循環返回一個值），該值將直接替換switch 表達式的操作數。

這個新的語法糖就類似在循環中指定變量作為 switch 操作數一樣，示例如下：

zig
// 以下兩個單元測試等價，使用新的語法糖顯著減少代碼的長度
// 可以簡單理解為類似 c 語言中的 `goto`
test "labeled switch" {
    foo: switch (@as(u8, 1)) {
        1 => continue :foo 2,
        2 => continue :foo 3,
        3 => return,
        4 => {},
        else => unreachable,
    }
    return error.Unexpected;
}

test "emulate labeled switch" {
    var op: u8 = 1;
    while (true) {
        switch (op) {
            1 => {
                op = 2;
                continue;
            },
            2 => {
                op = 3;
                continue;
            },
            3 => return,
            4 => {},
            else => unreachable,
        }
        break;
    }
    return error.Unexpected;
}

新的語法糖有時會更易於理解，例如在實現有限狀態自動機時，可以編寫 continue :fsa new_state 來表示狀態轉換。

同時現在可以使用帶標籤的 break 從 switch 中跳出來，此時可以得到 switch 表達式的操作數。如果是沒有標記的 break，那麼只會對 for 或者 while 生效。

與普通的 switch 語句不同，帶有一個或多個 continue 目標的標記 switch 語句不會在編譯時隱式求值（這類似於循環的行為）。然而，與循環一樣，可以通過在 comptime 上下文中求值這樣的表達式來強制進行編譯時求值。

生成的代碼特性 ​

這種語言結構旨在生成有助於 CPU 預測 switch 各個 case 之間分支的代碼，從而提高熱循環中的性能，特別是那些調度指令、評估有限狀態自動機（FSA）或執行類似基於 case 的評估的循環。為了實現這一點，生成的代碼可能與直觀預期的不同。

如果 continue 的操作數在編譯時已知，那麼它可以被翻譯為一個無條件分支到相關的 case。這樣的分支是完全可預測的，因此通常執行速度非常快。

如果操作數在運行時已知，那麼每個 continue 可以變成一個單獨的條件分支（理想情況下通過共享跳轉表）回到同一組潛在的分支目標。這種模式的優勢在於它通過提供不同的分支指令來幫助 CPU 的分支預測器，這些指令可以與不同的預測數據相關聯。例如，在評估 FSA 時，如果 case a 很可能會跟隨 case b，而 case c 很可能會跟隨 case d，那麼分支預測器可以使用 switch case 之間的直接跳轉來更準確地預測控制流，而基於循環的降級會導致狀態調度“摺疊”成單個間接分支或類似的情況，從而阻礙分支預測。

這種降級可能會增加代碼大小，相比於簡單的“循環中的 switch”降級，任何 Zig 實現當然可以自由地按照自己的意願降級這種語法，只要遵守語言語義。然而，官方的 ZSF 編譯器實現將嘗試匹配上述降級，特別是在 ReleaseFast 構建模式下。

更多見相關 PR：Updating Zig's tokenizer to take advantage of this feature resulted in a 13% performance boost.。

聲明字面量 ​

Zig 0.14.0 擴展了“enum literal”語法 (.foo)，引入了一項新功能，稱為“decl literals”。現在，枚舉字面量 .foo 不一定指代枚舉，而是可以使用結果位置語義（Result Location Semantics）引用目標類型上的任何聲明。例如，考慮以下示例：

zig
const S = struct {
    x: u32,
    const default: S = .{ .x = 123 };
};
test "decl literal" {
    const val: S = .default;
    try std.testing.expectEqual(123, val.x);
}
const std = @import("std");

由於 val 的初始化表達式對應的結果類型是 S，因此初始化實際上等同於 S.default。這在初始化結構體字段時特別有用，可以避免再次指定類型：

zig
const S = struct {
    x: u32,
    y: u32,
    const default: S = .{ .x = 1, .y = 2 };
    const other: S = .{ .x = 3, .y = 4 };
};
const Wrapper = struct {
    val: S = .default,
};
test "decl literal initializing struct field" {
    const a: Wrapper = .{};
    try std.testing.expectEqual(1, a.val.x);
    try std.testing.expectEqual(2, a.val.y);
    const b: Wrapper = .{ .val = .other };
    try std.testing.expectEqual(3, b.val.x);
    try std.testing.expectEqual(4, b.val.y);
}
const std = @import("std");

這也可以幫助避免 Faulty Default Field Values，可以看下面的例子：

zig
/// `ptr` 指向 `[len]u32`.
pub const BufferA = extern struct { ptr: ?[*]u32 = null, len: usize = 0 };
// 以上給出的默認值是想它默認為空
var empty_buf_a: BufferA = .{};
// 不過這樣做實際上是違背的開發規範，實際上你可以這樣寫：
var bad_buf_a: BufferA = .{ .len = 10 };
// 這樣處理並不安全，通過聲明字面量可以實現方便並且安全的表示值

/// `ptr` 指向 `[len]u32`.
pub const BufferB = extern struct {
    ptr: ?[*]u32,
    len: usize,
    pub const empty: BufferB = .{ .ptr = null, .len = 0 };
};
// 以一種更簡單的方式創建一個新的空 buffer
var empty_buf_b: BufferB = .empty;
// 不會再出現莫名其妙的字段覆蓋！
// 如果我們要指定值，那麼就需要都指定值，這會使錯誤更容易暴露出來：
var bad_buf_b: BufferB = .{ .ptr = null, .len = 10 };

許多現有的字段默認值使用可能更適合通過名為 default 或 empty 或類似的聲明來處理，以確保數據不變性不會因覆蓋單個字段而被破壞。

聲明字面量還支持函數調用，如下所示：

zig
const S = struct {
    x: u32,
    y: u32,
    fn init(val: u32) S {
        return .{ .x = val + 1, .y = val + 2 };
    }
};
test "call decl literal" {
    const a: S = .init(100);
    try std.testing.expectEqual(101, a.x);
    try std.testing.expectEqual(102, a.y);
}
const std = @import("std");

這種語法在初始化結構體字段時也很有用。它還支持通過 try 調用返回錯誤聯合的函數。以下示例結合使用這些功能來初始化一個圍繞 ArrayListUnmanaged 的薄包裝器：

zig
const Buffer = struct {
    data: std.ArrayListUnmanaged(u32),
    fn initCapacity(allocator: std.mem.Allocator, capacity: usize) !Buffer {
        return .{ .data = try .initCapacity(allocator, capacity) };
    }
};
test "initialize Buffer with decl literal" {
    var b: Buffer = try .initCapacity(std.testing.allocator, 5);
    defer b.data.deinit(std.testing.allocator);
    b.data.appendAssumeCapacity(123);
    try std.testing.expectEqual(1, b.data.items.len);
    try std.testing.expectEqual(123, b.data.items[0]);
}
const std = @import("std");

聲明字面量的引入伴隨著一些標準庫的變化。特別是，包括 ArrayListUnmanaged 和 HashMapUnmanaged 在內的非託管容器不應再使用 .{} 進行默認初始化，因為這裡的默認字段值違反了上述指導原則。相反，它們應該使用其 empty 聲明進行初始化，這可以通過聲明字面量方便地訪問：

zig
const Buffer = struct {
    foo: std.ArrayListUnmanaged(u32) = .empty,
};
test "default initialize Buffer" {
    var b: Buffer = .{};
    defer b.foo.deinit(std.testing.allocator);
    try b.foo.append(std.testing.allocator, 123);
    try std.testing.expectEqual(1, b.foo.items.len);
    try std.testing.expectEqual(123, b.foo.items[0]);
}
const std = @import("std");

類似地，std.heap.GeneralPurposeAllocator 現在應該使用其 .init 聲明進行初始化。

這些數據結構的過時默認字段值將在下一個發佈週期中移除。

字段和聲明不可重名 ​

Zig 0.14.0 引入了一項限制，即容器類型（結構體、聯合體、枚舉和不透明類型）不能有同名的字段和聲明（const/var/fn）。添加此限制是為了處理 MyEnum.foo 是查找聲明還是枚舉字段這一問題的歧義（這一問題因聲明字面量而加劇）。

通常，通過遵循標準命名約定可以避免這種情況：

zig
const Foo = struct {
    Thing: Thing,
    const Thing = struct {
        Data: u32,
    };
};

⬇️

zig
const Foo = struct {
    thing: Thing,
    const Thing = struct {
        data: u32,
    };
};

這一限制的一個好處是，文檔註釋現在可以明確地引用字段名稱，從而使這些引用成為可以點擊的超鏈接。

@splat 支持數組 ​

Zig 0.14.0 擴展了 @splat 內置函數，不僅適用於向量，還適用於數組，這在將數組默認初始化為常量值時非常有用。

例如，結合聲明字面量，我們可以優雅地初始化一個 "color" 值的數組：

zig
const Rgba = struct {
    r: u8,
    b: u8,
    g: u8,
    a: u8,
    pub const black: Rgba = .{ .r = 0, .g = 0, .b = 0, .a = 255 };
};
var pixels: [width][height]Rgba = @splat(@splat(.black));

操作數可以在編譯時已知或運行時已知。此外，該內置函數還可以用於初始化以哨兵值結尾的數組。

zig
const std = @import("std");
const assert = std.debug.assert;
const expect = std.testing.expect;
test "initialize sentinel-terminated array" {
    // the sentinel does not need to match the value
    const arr: [2:0]u8 = @splat(10);
    try expect(arr[0] == 10);
    try expect(arr[1] == 10);
    try expect(arr[2] == 0);
}
test "initialize runtime array" {
    var runtime_known: u8 = undefined;
    runtime_known = 123;
    // 操作數是運行時可知的，那麼返回一個運行時的數組
    const arr: [2]u8 = @splat(runtime_known);
    try expect(arr[0] == 123);
    try expect(arr[1] == 123);
}
test "initialize zero-length sentinel-terminated array" {
    var runtime_known: u8 = undefined;
    runtime_known = 123;
    const arr: [0:10]u8 = @splat(runtime_known);
    // 操作數在運行時已知，但由於數組長度為零，結果在編譯時已知。
    comptime assert(arr[0] == 10);
}

全局變量可以互相引用 ​

現在這段代碼是有效的：

zig
const std = @import("std");
const expect = std.testing.expect;

const Node = struct {
    next: *const Node,
};

const a: Node = .{ .next = &b };
const b: Node = .{ .next = &a };

test "example" {
    try expect(a.next == &b);
    try expect(b.next == &a);
}

@export 使用指針 ​

此版本的 Zig 簡化了 @export 內置函數。在之前的 Zig 版本中，這個內置函數的第一個操作數在語法上似乎是要導出的值，這個值被限制為局部變量或容器級聲明的標識符或字段訪問。這種系統限制過多，而且在語法上令人困惑且不一致；導出常量編譯時已知的值是合理的，而這種用法暗示了值被導出，但實際上其地址才是相關的信息。為了解決這個問題，@export 現在有了一個新的用法，與 @extern 非常相似；它的第一個操作數是一個指針，指向要導出的數據。在大多數情況下，解決這個問題只需添加一個 & 操作符。

zig
const foo: u32 = 123;
test "@export" {
    @export(foo, .{ .name = "bar" });
}

⬇️

zig
const foo: u32 = 123;
test "@export" {
    @export(&foo, .{ .name = "bar" });
}

@branchHint 替換 @setCold ​

在高性能代碼中，有時希望向優化器提示條件的哪個分支更可能被執行；這可以生成更高效的機器代碼。一些語言通過在布爾條件上添加 "likely" 註釋來實現這一點；例如，GCC 和 Clang 實現了 __builtin_expect 函數。Zig 0.14.0 引入了一種機制來傳達此信息：新的 @branchHint(comptime hint: std.builtin.BranchHint) 內置函數。這個內置函數不是修改條件，而是作為塊中的第一個語句出現，以傳達控制流是否可能到達相關塊。

例如：

zig
fn warnIf(cond: bool, message: []const u8) void {
    if (cond) {
        @branchHint(.unlikely); // we expect warnings to *not* happen most of the time!
        std.log.warn("{s}", message);
    }
}
const std = @import("std");

BranchHint 類型如下：

zig
pub const BranchHint = enum(u3) {
    /// Equivalent to no hint given.
    none,
    /// This branch of control flow is more likely to be reached than its peers.
    /// The optimizer should optimize for reaching it.
    likely,
    /// This branch of control flow is less likely to be reached than its peers.
    /// The optimizer should optimize for not reaching it.
    unlikely,
    /// This branch of control flow is unlikely to *ever* be reached.
    /// The optimizer may place it in a different page of memory to optimize other branches.
    cold,
    /// It is difficult to predict whether this branch of control flow will be reached.
    /// The optimizer should avoid branching behavior with expensive mispredictions.
    unpredictable,
};

除了作為條件之後塊的第一個語句外，@branchHint 也允許作為任何函數的第一個語句。期望是優化器可以將可能性信息傳播到包含這些調用的分支；例如，如果某個控制流分支總是調用一個標記為 @branchHint(.unlikely) 的函數，那麼優化器可以假設該分支不太可能被執行。

BranchHint 包含 .cold ，這導致舊的 @setCold 功能已經多餘，@setCold 已被移除。在大多數情況下，遷移非常簡單：只需將 @setCold(true) 替換為 @branchHint(.cold)：

zig
fn foo() void {
    @setCold(true);
    // ...
}

⬇️

zig
fn foo() void {
    @branchHint(.cold);
    // ...
}

但是，需要注意 @branchHint 必須是封閉塊（函數）中的第一個語句。這一限制在 @setCold 中不存在，因此非常規的用法可能需要額外做點小改動：

zig
fn foo(comptime x: u8) void {
    if (x == 0) {
        @setCold(true);
    }
    // ...
}

⬇️

zig
fn foo(comptime x: u8) void {
    @branchHint(if (x == 0) .cold else .none);
    // ...
}

移除 @fence ​

在 Zig 0.14 中，@fence 已被移除。原本提供 @fence 是為了與 C11 內存模型保持一致，但它通過修改所有先前和未來原子操作的內存排序來使語義複雜化。這會產生難以在檢測器中建模的不可預見的約束。fence 操作可以通過升級原子內存排序或添加新的原子操作來替代。

@fence 的最常見用例可以通過利用更強的內存排序或引入新的原子變量來替代。

StoreLoad 屏障 ​

最常見的用例是 @fence(.seq_cst)。這主要用於確保對不同原子變量的多個操作之間的一致順序。

例如：

thread-1thread-2
store X // Astore Y // C
fence(seq_cst) // F1fence(seq_cst) // F2
load Y // Bload X // D

目標是確保要麼 load X (D) 看到 store X (A)，要麼 load Y (B) 看到 store Y (C)。這一對順序一致的柵欄通過兩個不變12來保證這一點。

現在 @fence 已被刪除，還有其他方法可以實現這種關係：

  • 將所有相關的存儲和加載（A、B、C 和 D）設為 SeqCst，將它們全部包含在總順序中。
  • 將存儲操作（A/C）設為 Acquire，並將其匹配的加載操作（D/B）設為 Release。從語義上講，這意味著將它們升級為讀 - 修改 - 寫操作，這可以實現這樣的排序。加載操作可以替換為非變異的 RMW 操作，即 fetchAdd(0) 或 fetchOr(0)。

像 LLVM 這樣的優化器可能會在內部將其簡化為 @fence(.seq_cst) + load。

條件屏障 ​

fence 的另一個用例是分別使用 Acquire 或 Release 有條件地與先前或未來的原子操作創建同步關係。

一個簡單示例是原子引用計數器：

zig
fn inc(counter: *RefCounter) void {
  _ = counter.rc.fetchAdd(1, .monotonic);
}

fn dec(counter: *RefCounter) void {
  if (counter.rc.fetchSub(1, .release) == 1) {
      @fence(.acquire);
      counter.deinit();
  }
}

在 fetchSub(1) 中的加載操作只需要在最後一次引用計數遞減時為 Acquire，以確保之前的遞減發生在 deinit() 之前。這裡的 @fence(.acquire) 使用 fetchSub(1) 的加載部分創建了這種關係。

如果沒有 @fence ，這裡有兩種方法：

  • 無條件地通過柵欄的排序來加強所需的原子操作。
zig
if (counter.rc.fetchSub(1, .acq_rel) == 1) {
  • 有條件地複製所需的存儲或加載，並按照柵欄的順序進行
zig
if (counter.rc.fetchSub(1, .release) == 1) {
    _ = counter.rc.load(.acquire);

Acquire 將與 rc 修改順序中的最長釋放序列同步，使所有先前的遞減操作發生在 deinit() 之前。

同步外部操作 ​

@fence 最不常見的用法是為程序員無法控制的原子操作（例如外部函數調用）提供額外的同步。在這種情況下使用 @fence 依賴於隱式函數具有不理想的弱排序的原子操作。

理想情況下，隱式函數應該對用戶可訪問，他們可以簡單地在源代碼中增加排序。但如果這不可能，最後的手段是引入一個原子變量來模擬柵欄的屏障。例如：

thread-1thread-2
queue.push()e = signal.listen()
fence(.seq_cst)fence(.seq_cst)
signal.notify()if queue.empty(): e.wait()
thread-1thread-2
queue.push()e = signal.listen()
fetchAdd(0, .seq_cst)fetchAdd(0, .seq_cst)
signal.notify()if queue.empty(): e.wait()

packed 結構體相等性 ​

現在可以直接比較 packed 結構體，而無需通過 @bitCast 轉換為底層整數類型。

zig
const std = @import("std");
const expect = std.testing.expect;

test "packed struct equality" {
    const S = packed struct {
        a: u4,
        b: u4,
    };
    const x: S = .{ .a = 1, .b = 2 };
    const y: S = .{ .b = 2, .a = 1 };
    try expect(x == y);
}

原子 packed 結構體 ​

移除匿名結構類型，統一元組 ​

此更改重新設計了匿名結構體字面量和元組的工作方式。

以前，一個無類型的匿名結構體字面量（例如 const x = .{ .a = 123 }）被賦予了一個“匿名結構體類型”，這是一種特殊的結構體，通過結構等價進行強制轉換。這種機制是我們使用結果位置語義作為類型推斷的主要機制之前的遺留機制。此更改將語言更改為在此處分配的類型為“普通”結構體類型。它使用一種基於 AST 節點和類型結構的等價形式，非常類似於具體化的 (@Type) 類型。

此外，元組也被簡化了。“簡單”元組類型和“複雜”元組類型之間的區別被消除了。所有元組，即使是那些使用 struct { ... } 語法顯式聲明的元組，也使用結構等價，並且不進行分階段類型解析。元組的限制非常嚴格：它們不能有非自動佈局，不能有對齊字段，不能有默認值（編譯時字段除外）。元組目前沒有優化佈局，但這在未來可以更改。

此更改簡化了語言，並修復了一些通過指針進行的導致非直觀行為的問題強制轉換。

調用約定增強並且替換 @setAlignStack ​

Zig 允許使用 callconv(...) 聲明函數的調用約定，其中括號中的值是類型為 std.builtin.CallingConvention。在之前的 Zig 版本中，這種類型是一個簡單的枚舉，列出了一些常見的調用約定，例如 x86 的 .Stdcall 和 ARM 的 .AAPCS。 .C 指的是目標的默認 C 調用約定。

Zig 0.14.0 將 CallingConvention 實現更加詳細：它現在包含了 Zig 當前支持的每個目標的每個主要調用約定。例如 .x86_64_sysv、.arm_aapcs 和 .riscv64_interrupt。此外，CallingConvention 現在是一個標記聯合類型，而不是枚舉，這允許在調用約定上指定選項。

大多數可用的調用約定都有一個 std.builtin.CallingConvention.CommonOptions 的有效負載，這允許在調用函數時覆蓋預期的堆棧對齊：

zig
/// Options shared across most calling conventions.
pub const CommonOptions = struct {
    /// The boundary the stack is aligned to when the function is called.
    /// `null` means the default for this calling convention.
    incoming_stack_alignment: ?u64 = null,
};

這在與使用 -mpreferred-stack-boundary GCC 標誌編譯的 C 代碼交互時非常有用。

少數調用約定具有更復雜的選項，例如：

zig
/// Options for x86 calling conventions which support the regparm attribute to pass some
/// arguments in registers.
pub const X86RegparmOptions = struct {
    /// The boundary the stack is aligned to when the function is called.
    /// `null` means the default for this calling convention.
    incoming_stack_alignment: ?u64 = null,
    /// The number of arguments to pass in registers before passing the remaining arguments
    /// according to the calling convention.
    /// Equivalent to `__attribute__((regparm(x)))` in Clang and GCC.
    register_params: u2 = 0,
};

默認的 C 調用約定不再由一個特殊標籤表示。相反，CallingConvention 包含一個名為 c 的聲明，其定義如下：

zig
/// This is an alias for the default C calling convention for this target.
/// Functions marked as `extern` or `export` are given this calling convention by default.
pub const c = builtin.target.cCallingConvention().?;

結合聲明字面量，這允許編寫 callconv(.c) 來指定此調用約定。

Zig 0.14.0 包含名為 Unspecified、C、Naked、Stdcall 等聲明，以允許現有的 callconv 用法繼續工作，這要歸功於聲明字面量。這些聲明已被棄用，並將在未來的 Zig 版本中移除。

多數調用約定都有一個 incoming_stack_alignment 選項，用於指定調用函數時堆棧將對齊的字節邊界，這可以用於與使用低於 ABI 要求的堆棧對齊的代碼進行互操作。以前，@setAlignStack 內置函數可以用於這種情況；然而，它的行為定義得不太明確，並且將其應用於這種情況需要了解 ABI 的預期堆棧對齊。因此，@setAlignStack 內置函數已被移除。相反，用戶應該在他們的 callconv 上註釋預期的堆棧對齊，允許優化器在必要時重新對齊。這也允許優化器在調用這樣的函數時避免不必要的堆棧重新對齊。為了方便起見，CallingConvention 有一個 withStackAlign 函數，可以用來改變傳入的堆棧對齊。

遷移很簡單：

zig
// This function will be called by C code which uses a 4-byte aligned stack.
export fn foo() void {
    // I know that my target's ABI expects a 16-byte aligned stack.
    @setAlignStack(16);
    // ...
}

⬇️

設計思路：

每個線程都有一個單獨的空閒列表，但是，當線程退出時，數據必須是可恢復的。我們不會直接知道線程何時退出，因此有時一個線程必須嘗試回收另一個線程的資源。

超過一定大小的分配直接進行內存映射，不存儲分配元數據。這是可行的，因為這個分配器實現拒絕 resize（將從小的 buffer 移動到大的 buffer 或反過來的行為）。

每個分配器操作從線程局部變量檢查線程標識符，以確定訪問全局狀態中的哪個元數據，並嘗試獲取其鎖。這通常會在沒有爭用的情況下成功，除非另一個線程被分配了相同的 ID。在這種爭用的情況下，線程會移動到下一個線程元數據槽，並重復嘗試獲取鎖的過程。

通過將線程局部元數據數組限制為與 CPU 數量相同，確保隨著線程的創建和銷燬，它們循環通過整個空閒列表集。

要使用這個新的 allocator，在你的主函數中放置類似以下內容的代碼：

zig
var debug_allocator: std.heap.DebugAllocator(.{}) = .init;

pub fn main() !void {
    const gpa, const is_debug = gpa: {
        if (native_os == .wasi) break :gpa .{ std.heap.wasm_allocator, false };
        break :gpa switch (builtin.mode) {
            .Debug, .ReleaseSafe => .{ debug_allocator.allocator(), true },
            .ReleaseFast, .ReleaseSmall => .{ std.heap.smp_allocator, false },
        };
    };
    defer if (is_debug) {
        _ = debug_allocator.deinit();
    };
}

Allocator API 變動 (remap) ​

此版本在 std.mem.Allocator.VTable 中引入了一個新函數 remap。

以下為文檔註釋中的關鍵部分：

嘗試擴展或縮小內存，允許重新定位。

非空返回值表示調整大小成功。

分配可能具有相同的地址，或者可能已重新定位。

在任何一種情況下，分配現在的大小都是 new_len。

空返回值表示調整大小相當於分配新內存，從舊內存複製字節，然後釋放舊內存。

在這種情況下，調用者執行復制操作更為高效。

函數原型：

remap: *const fn (*anyopaque, memory: []u8, alignment: Alignment, new_len: usize, return_address: usize) ?[*]u8,

所有 Allocator.VTable 函數現在接受 std.mem.Alignment 類型而不是 u8。具體數值相同，但現在有類型安全和附加到類型的便捷方法。

resize 和 remap 各有其用途。例如，resize 對於 std.heap.ArenaAllocator 是必要的，因為它不能重新定位其分配。同時，當容量增加時，remap 適用於 std.ArrayList。

關於 remap 需要注意，除非可以在不執行分配器內部 memcpy 的情況下實現 remap，否則 Allocator 實現 remap 通常應與 resize 行為相同。

例如，此版本在支持的情況下引入了對調用 mremap 的支持，在這種情況下，操作系統重新映射頁面，避免了用戶空間中昂貴的 memcpy。Zig 程序員現在可以期望在使用 std.heap.page_allocator 以及將其用作例如 std.heap.ArenaAllocator 或 std.heap.GeneralPurposeAllocator 的後備分配器時發生這種情況。

另外：

  • std.heap.page_allocator 現在支持大於頁面大小的對齊，這在重寫 DebugAllocator 時是需要的。
  • 刪除 std.heap.WasmPageAllocator，改用 std.heap.WasmAllocator。
  • 刪除 std.heap.LoggingAllocator，它不屬於 std。
  • 刪除 std.heap.HeapAllocator - 這是僅限 Windows 的，並且依賴於 kernel32。

新的包哈希格式 ​

舊的哈希格式如下所示：1220115ff095a3c970cc90fce115294ba67d6fbc4927472dc856abc51e2a1a9364d7

新的哈希格式如下所示：mime-3.0.0-zwmL-6wgAADuFwn7gr-_DAQDGJdIim94aDIPa6qO-6GT

除了 200 位的 SHA-256，新哈希還包含以下附加數據：

  • 名稱
  • 版本
  • 指紋的 ID 組件
  • 磁盤上的總解壓大小

這在編譯錯誤或文件路徑中顯示包哈希時提供了更好的用戶體驗，並提供了實現依賴樹管理工具所需的數據。例如，僅通過了解整個依賴樹的包哈希，現在可以知道在完成所有獲取後磁盤上所需的總文件大小，以及執行版本選擇，而無需進行任何獲取。

文件大小還可以作為默認情況下是否獲取懶加載包的啟發式方法。

這些好處需要一些新的規則來管理 build.zig.zon 文件：

  • 名稱和版本限制為 32 字節。
  • 名稱必須是有效的裸 Zig 標識符。將來，這一限制可能會被取消；目前選擇了保守的規則。

指紋是一個重要的概念：

  • 與名稱一起，這代表了一個全局唯一的包標識符。該字段在包首次創建時由工具鏈自動初始化，然後永遠不會更改。儘管生態系統是去中心化的，但這允許 Zig 明確檢測一個包是否是另一個包的更新版本。
  • 當分叉一個 Zig 項目時，如果上游項目仍在維護，則應重新生成此指紋。否則，分叉是敵對的，試圖控制原始項目的身份。可以通過刪除該字段並運行 zig build 來重新生成指紋。
  • 這個 64 位整數是 32 位 ID 組件和 32 位校驗和的組合。

指紋中的 ID 組件有以下限制：

  • 0x00000000 保留用於舊包。
  • 0xffffffff 保留用於表示“裸”包。

校驗和是從名稱計算的，用於保護 Zig 用戶免受意外的 ID 衝突。

版本選擇和利用指紋的相關工具尚未實現。

儘管仍支持舊的哈希格式，但此更改會破壞任何不遵循上述新包命名規則的包。還有一個已知的錯誤：不必要地獲取舊包。

        .optimize = .ReleaseSafe,
    });
    const run_gen = b.addRunArtifact(generator);
    const generated_file = run_gen.addOutputFileArg("generated.zig");
    b.addNamedLazyPath("generated", generated_file);
}

addLibrary 函數 ​

作為 addSharedLibrary 和 addStaticLibrary 的替代，但可以更輕鬆地在 build.zig 中更改鏈接模式，例如：

對於庫來說：

zig
const lib = b.addLibrary(.{
    .linkage = linkage,
    .name = "foo_bar",
    .root_module = mod,
});

對於調用庫的包來說：

zig
const dep_foo_bar = b.dependency("foo_bar", .{
    .target = target,
    .optimize = optimize,
    .linkage = .dynamic // or leave for default static
});

mod.linkLibrary(dep_foo_bar.artifact("foo_bar"));
